# render-service-manager

A single, config-driven service manager for scheduled services on **Render free tier** (512 MB). One process, one URL for the external cron, one file to touch when something changes: `services.yaml`.

```
cron-job.org ──GET/POST /tick (X-Auth-Token)──▶  Render (Docker, single uvicorn process)
   (every 5 min)                                        │
                                                       ├─ daily script fetch from GitHub
                                                       ├─ committer tick → GitHub commits spread over working hours
                                                       ├─ t2g tick       → ssh to the cluster → chain_tick.sh
                                                       └─ credit tick    → OpenRouter → Upstash Redis
                                              /committer /t2g /credit  → the services' original APIs
```

## Why Docker

The cluster driver (`t2g`) runs `ssh`/`scp` **via subprocess**, so the binaries must exist in the runtime. Render's official docs list the tools shipped with the *native* Python runtime (Debian 12: curl, git, rsync, ...) and **`ssh`/`scp` are not among them**, nor is there a supported way to install system packages in the native runtime ([native runtimes — tools and utilities](https://render.com/docs/native-runtimes#tools-and-utilities)). With Docker, the `Dockerfile` installs `openssh-client` explicitly — guaranteed. Free tier RAM is the same 512 MB in both runtimes ([compute plans](https://render.com/docs/compute-plans)).

**Does Docker start automatically on Render?** Yes. A Docker web service is built and launched by the platform on every deploy or restart — you never start it manually. This is also what backs the manager's restart-on-script-update: the process exits after flushing the response, and Render relaunches the container with the fresh code. (Local Docker Desktop, by contrast, must be started by you for local container tests.)

## Structure

```
.  (repo root — the Dockerfile is already here)
├── app.py                   # the service manager (single FastAPI process)
├── sources.py               # script fetch from GitHub (parallel, hash-compared)
├── services.yaml            # ★ THE SECRET MANIFEST (gitignored, never published)
├── services.yaml.example    # public reference manifest
├── requirements.txt         # dependencies of ALL services (union) — see Limitations
├── Dockerfile               # python:3.12-slim + openssh-client
├── render.yaml              # Render blueprint (Docker, free plan, /health check)
├── .env.example             # environment variables template
├── README.md                # this file
└── API_GUIDELINES.md        # conventions for uniform service APIs
```

Runtime directories (`services/`, `state/`, `data/`, `state.json`) are generated by the manager itself and are gitignored. An optional local-only `fallback/` directory (also gitignored) can hold last-known-good copies of the service scripts to seed a boot when GitHub is unreachable — see "How updates work".

## The `services.yaml` manifest

The manifest is **secret**: it describes your services and their repos, so it is gitignored and **never published** — the repo ships `services.yaml.example` as a public reference. At boot the manager resolves the real manifest in this order:

1. **`MANIFEST_CONTENT`** env var — the whole YAML as an env var (multiline with literal `\n`, exactly like an SSH key on Render);
2. **`MANIFEST_REPO`** env var — a **private GitHub repository** acting as a manifest deposit: the manager fetches `services.yaml` from it via the Contents API with `GITHUB_TOKEN` (optional `MANIFEST_BRANCH`, default `main`, and `MANIFEST_PATH`, default `services.yaml`);
3. a **local `services.yaml` file** (development).

If none is available, the manager still boots (health OK) but `/status` shows `config_error: services.yaml not found` and no service runs.

On Render the simplest channel is a **Secret File** (dashboard → Environment → Secret Files): upload the plain multiline `services.yaml` with filename `services.yaml` — Render mounts it under `/etc/secrets/` and links it at the app root, so the manager reads it as the local file (and if only the `/etc/secrets` copy exists, the manager copies it from there). With the Secret File in place you can leave `MANIFEST_CONTENT` and `MANIFEST_REPO` unset.

One block per service. Fields:

| Field | Meaning |
|---|---|
| `display_name`, `description` | Presentation (shown in `GET /services`) |
| `source.mode` | `raw` (public repo, no token) or `api` (private repo: Contents API + `GITHUB_TOKEN`) |
| `source.repo`, `source.branch` | Where to fetch from — `${VAR}` placeholders supported |
| `source.files[]` | `repo_path` → `dest` pairs (`dest` lives under `services/`) |
| `entry` | The main script imported as a module |
| `env.required` | If even one variable is missing → the service is disabled with a clear message |
| `env.optional` | Defaults applied via `setdefault` when the variable is unset |
| `dependencies` | Informational: the manager checks they are installed and warns |
| `setup_dirs`, `setup[]` | mkdir + functions called after import (lifespan equivalent) |
| `api.mount` | Where the original sub-app is mounted (e.g. `/t2g` → the TUI points there) |
| `api.auth` | `manager` (manager token) or `service` (the service has its own internal auth) |
| `api.public_paths` | Paths exempt from the manager token (e.g. credit's browser dashboard) |
| `api.endpoints` | Documentation of the original routes (shown in `GET /services/{name}`) |
| `actions` | Uniform actions: name → `{function, sync, timeout_s}` → `GET|POST /services/{name}/{action}` |
| `schedule.mode` | `every_tick` · `interval_minutes` (+ `interval_minutes: N`) · `disabled` |

### `${VAR}` placeholders

The published manifest contains no personal data: repos, owners and hosts live only in environment variables (local: `.env` · Render: dashboard). Placeholders such as `${COMMITTER_REPO}` are substituted when the config is loaded; missing variables produce a warning in the log and stay literal, which makes them visible in fetch errors.

## Manager endpoints

| Endpoint | Description |
|---|---|
| `GET\|POST /tick` | **The external cron calls this every 5 minutes.** Runs every service's tick according to its schedule, plus the daily fetch on the first tick of the day. Overlap lock (409 if the previous tick is still running) |
| `GET /fetch` | Updates the scripts from GitHub immediately; if content changed → clean restart that reloads the code (10-minute anti-flapping guard) |
| `GET /services` | Service list from the manifest, with load status |
| `GET /services/{name}` | Detail of one service |
| `GET\|POST /services/{name}/{action}` | A single service's action: e.g. `GET /services/t2g/status`, `POST /services/committer/tick` |
| `GET /status` | Aggregate state: services + last tick + per-service status |
| `GET /health` | Health check (no auth) — used by Render |
| `/{name}/...` | The service's ORIGINAL APIs, mounted 1:1 (e.g. `POST /t2g/jobs`, `GET /credit/api/data`) |

`/tick` response (real, from the local test):

```json
{
  "ok": true,
  "fetch": {"skipped": true},
  "services": {
    "committer": {"ok": true, "ms": 0,    "data": {"status": "sleeping", "reason": "outside working hours"}},
    "t2g":       {"ok": true, "ms": 1358, "data": {"cluster_reachable": true, "active_job": null, "queue": []}},
    "credit":    {"ok": true, "ms": 324,  "data": {"status": "ok", "entry": {"balance": 12.34}}}
  }
}
```

## Local run

### Without Docker (recommended locally: reuses the ssh alias from your `~/.ssh/config`)

```powershell
copy .env.example .env        # then fill in the values (set RESTART_ON_CHANGE=0 locally!)
uv venv --python 3.12 .venv
uv pip install -r requirements.txt --python .venv\Scripts\python.exe
.venv\Scripts\python.exe -m uvicorn app:app --port 8765
curl http://localhost:8765/health
curl -H "X-Auth-Token: <token>" http://localhost:8765/tick
```

The t2g service's own TUI can point at the manager: `.../t2g` with its `X-Auth-Token`.

### With Docker (reproduces Render exactly)

```powershell
docker build -t render-manager .
docker run --rm -p 8000:10000 --env-file .env render-manager
# NB: inside the container there are NO ~/.ssh/config aliases:
#     you need T2G_SSH_HOST=<login-node>, T2G_SSH_USER and T2G_SSH_KEY_CONTENT
```

## Deploying to Render (step by step)

1. **Create a GitHub repository** and push this folder as is (the Dockerfile is already at the root — the build context is the root).
2. **Render → New → Web Service** → connect the repo (or use the `render.yaml` blueprint: Docker, free plan and the `/health` health check are preconfigured).
3. **Environment / Secret Files** (Render dashboard) — see the table below. **First of all the secret manifest**: upload it as a **Secret File** named `services.yaml` (Environment → Secret Files; plain multiline YAML, no escaping) — recommended — or set `MANIFEST_CONTENT` / `MANIFEST_REPO`. Then at minimum: `MANAGER_AUTH_TOKEN`, `GITHUB_TOKEN`, `COMMITTER_REPO`, `CREDIT_REPO`, `T2G_REPO`, `T2G_AUTH_TOKEN`, `T2G_SSH_USER`, `T2G_SSH_HOST`, `T2G_SSH_KEY_CONTENT`, `OPENROUTER_API_KEY`, `UPSTASH_REDIS_URL`, `UPSTASH_REDIS_TOKEN` (the committer numeric defaults are already in the blueprint).
4. **Dedicated SSH key** for the cluster login node: `ssh-keygen -t ed25519 -f ~/.ssh/t2g_driver -N ""`, authorize it on the cluster, then paste it on Render with literal `\n`: `awk '{printf "%s\\n", $0}' ~/.ssh/t2g_driver`.
5. **cron-job.org**: ONE cron job, every 5 minutes, `GET https://<service>.onrender.com/tick` with header `X-Auth-Token: <MANAGER_AUTH_TOKEN>` and a generous timeout (90-120 s, cold starts).
6. **Shut down the old services** and their crons (the manager replaces them).
7. **TUI**: point `T2G_SERVICE_URL` to `https://<service>.onrender.com/t2g`.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `MANAGER_AUTH_TOKEN` | recommended | Protects every route except `/health` and the `public_paths`; also accepts `T2G_AUTH_TOKEN` |
| `SERVICES_ENABLED` | no | Default: all services. For targeted tests: `committer`, `t2g`, `credit`, or empty |
| `DAILY_FETCH` | no | `1` (default) = automatic daily fetch; `0` = manual `/fetch` only |
| `RESTART_ON_CHANGE` | no | `1` (default) = restart after script updates; set `0` locally |
| `TIMEZONE_OFFSET` | no | `2` (default) — used for the fetch "day" and by committer |
| Secret manifest | yes on Render | **Render Secret File** `services.yaml` (recommended, plain YAML) **or** `MANIFEST_CONTENT` **or** `MANIFEST_REPO` (+ optional `MANIFEST_BRANCH`/`MANIFEST_PATH`) |
| Service sources | yes | `COMMITTER_REPO`, `CREDIT_REPO`, `T2G_REPO` — fill the manifest's `${VAR}` placeholders |
| Committer | — | `GITHUB_TOKEN`, `GITHUB_REPO`, `GITHUB_USERNAME`, `BASE_COMMITS` (10), `DELTA_COMMITS` (2), `WORK_START_HOUR` (9), `WORK_END_HOUR` (18) |
| T2G | — | `T2G_AUTH_TOKEN`, `T2G_SSH_USER`, `T2G_SSH_HOST` (on Render: explicit login node host), `T2G_SSH_KEY_CONTENT`, `T2G_SSH_TIMEOUT` (30) |
| Credit | — | `OPENROUTER_API_KEY`, `UPSTASH_REDIS_URL`, `UPSTASH_REDIS_TOKEN` (the names WITHOUT `*_REST_*`: those are what the code reads) |

## How updates work

- **Every day**, on the first `/tick`, the manager downloads the scripts from the source repos. If content changed → clean restart → fresh code. `GET /fetch` forces it immediately.
- **Failed fetch** (repo down or unreachable) → existing copies are used and the fetch **retries at every tick** until it succeeds (self-healing). At boot, if nothing is on disk and a local `fallback/` exists (gitignored, optional), it seeds from there.
- A **new pip dependency** appearing in a script → add it to the manager's `requirements.txt` and redeploy: the fetch does NOT install packages. The manager logs a warning about missing dependencies at boot.

## Known limitations

- Render's filesystem is ephemeral: `state.json` (committer) and the SQLite cache (t2g) reset on every redeploy — by design, the original services are built that way (t2g's source of truth is the cluster; committer re-initializes the day).
- A very unlucky tick (slow fetch + all services) can take ~3-4 minutes: cron-job.org must not overlap ticks (every 5 minutes is fine; the manager also rejects overlapping ticks with 409).
- If GitHub is unreachable at boot AND no local `fallback/` exists, services stay `script missing` until the first successful fetch (retried at every tick, then an automatic restart loads them).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `/status` shows `config_error: services.yaml not found` | no manifest on Render | set `MANIFEST_CONTENT` or `MANIFEST_REPO` (+ optional `MANIFEST_BRANCH`/`MANIFEST_PATH`) |
| Service `"loaded": false` in `/services` | missing env vars or import error | the `error` field says exactly what is missing |
| `POST /t2g/...` → 502 cluster unreachable | ssh key/host/user issues | check the `T2G_*` env vars and the dedicated key on Render |
| `fetch` errors 404 in `/tick` | private repo unreachable with the token | check `GITHUB_TOKEN` and the service source env vars |
| committer tick always `sleeping` | outside working hours | normal: 9:00-18:00 local time (configurable) |
| Continuous restarts after a push | anti-flapping guard (10 min) | expected: at most one restart every 10 minutes |
| TUI cannot connect | wrong token or URL | URL `.../t2g` + `X-Auth-Token` header (see API_GUIDELINES) |
