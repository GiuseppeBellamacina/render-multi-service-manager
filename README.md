# render-service-manager

A single, config-driven service manager for scheduled services on **Render free tier** (512 MB). One process, one URL for the external cron, one file to touch when something changes: `services.yaml`.

```
cron-job.org ──GET/POST /tick (X-Auth-Token)──▶  Render (Docker, single uvicorn process)
   (every 5 min)                                        │
                                                        ├─ daily script fetch from GitHub
                                                        ├─ ticker tick  → one unit of ticker's work
                                                        └─ sampler tick → one unit of sampler's work
                                                     /ticker /sampler  → the services' original APIs
```

## Why Docker

A managed service may need `ssh`/`scp` at runtime (for example to reach a remote host over SSH): it runs them **via subprocess**, so the binaries must exist in the runtime. Render's official docs list the tools shipped with the *native* Python runtime (Debian 12: curl, git, rsync, ...) and **`ssh`/`scp` are not among them**, nor is there a supported way to install system packages in the native runtime ([native runtimes — tools and utilities](https://render.com/docs/native-runtimes#tools-and-utilities)). With Docker, the `Dockerfile` installs `openssh-client` explicitly — guaranteed. Free tier RAM is the same 512 MB in both runtimes ([compute plans](https://render.com/docs/compute-plans)).

**Does Docker start automatically on Render?** Yes. A Docker web service is built and launched by the platform on every deploy or restart — you never start it manually. This is also what backs the manager's restart-on-script-update: the process exits after flushing the response, and Render relaunches the container with the fresh code. (Local Docker Desktop, by contrast, must be started by you for local container tests.)

## Structure

```
.  (repo root — the Dockerfile is already here)
├── app.py                   # the service manager (single FastAPI process)
├── sources.py               # script fetch from GitHub (parallel, hash-compared)
├── services.yaml            # ★ THE SECRET MANIFEST (gitignored, never published)
├── services.yaml.example    # public reference manifest
├── pyproject.toml           # dependencies of ALL services (union) + tool config — see Limitations
├── uv.lock                  # exact pinned versions: what the image installs
├── Dockerfile               # python:3.12-slim + openssh-client + uv
├── .env.example             # environment variables template
├── format.ps1               # isort + black + ruff (tools from .venv)
├── README.md                # this file
└── API_GUIDELINES.md        # conventions for uniform service APIs
```

Runtime directories (`services/`, `state/`, `data/`, `state.json`) are generated by the manager itself and are gitignored. An optional local-only `fallback/` directory (also gitignored) can hold last-known-good copies of the service scripts to seed a boot when GitHub is unreachable — see "How updates work".

## The `services.yaml` manifest

The manifest is **secret**: it describes your services and their repos, so it is gitignored and **never published** — the repo ships `services.yaml.example` as a public reference. At boot the manager resolves the real manifest in this order:

1. **`MANIFEST_CONTENT`** env var — the whole YAML as an env var (multiline with literal `\n`, exactly like an SSH key on Render);
2. **`MANIFEST_REPO`** env var — a **private GitHub repository** acting as a manifest deposit: the manager fetches `services.yaml` from it via the Contents API with `GITHUB_TOKEN` (optional `MANIFEST_BRANCH`, default `main`, and `MANIFEST_PATH`, default `services.yaml`);
3. **`MANIFEST_FILE`** env var — an explicit file path, e.g. `/etc/secrets/services.yaml` when using a Render Secret File;
4. a **local `services.yaml` file** (development; a Render Secret File linked at the app root lands here, and `/etc/secrets/services.yaml` is picked up automatically even without `MANIFEST_FILE`).

If none is available, the manager still boots (health OK) but `/status` shows `config_error: services.yaml not found` and no service runs.

On Render the simplest channel is a **Secret File** (dashboard → Environment → Secret Files): upload the plain multiline `services.yaml` with filename `services.yaml` — Render mounts it under `/etc/secrets/` and links it at the app root, so the manager reads it as the local file (and if only the `/etc/secrets` copy exists, the manager copies it from there). With the Secret File in place you can leave `MANIFEST_CONTENT` and `MANIFEST_REPO` unset (`MANIFEST_FILE=/etc/secrets/services.yaml` makes the pointer explicit — optional). The same mechanism works for any other secret a service needs (e.g. an SSH private key): upload it as a Secret File (e.g. `my_ssh_key`, plain multiline) and point the service's key-file env var at `/etc/secrets/my_ssh_key` — at boot the manager normalizes it to a local `0600` file, so ssh's strict key-permission check always passes.

One block per service. Fields:

| Field | Meaning |
|---|---|
| `display_name`, `description` | Presentation (shown in `GET /services`) |
| `source.mode` | `raw` (public repo, no token) or `api` (private repo: Contents API + `GITHUB_TOKEN`) |
| `source.repo`, `source.branch` | Where to fetch from — `${VAR}` placeholders supported |
| `source.files[]` | `repo_path` → `dest` pairs (`dest` lives under `services/`) |
| `entry` | The main script imported as a module |
| `env.required` | If even one variable is missing → the service is disabled with a clear message |
| `env.optional` | Defaults applied via `setdefault` when the variable is unset |
| `dependencies` | Informational: the manager checks they are installed and warns |
| `setup_dirs`, `setup[]` | mkdir + functions called after import (lifespan equivalent) |
| `api.mount` | Where the original sub-app is mounted (e.g. `/sampler`) |
| `api.auth` | `manager` (manager token) or `service` (the service has its own internal auth) |
| `api.public_paths` | Paths exempt from the manager token (e.g. a browser dashboard that cannot send headers) |
| `api.endpoints` | Documentation of the original routes (shown in `GET /services/{name}`) |
| `actions` | Uniform actions: name → `{function, sync, timeout_s}` → `GET|POST /services/{name}/{action}` |
| `schedule.mode` | `every_tick` · `interval_minutes` (+ `interval_minutes: N`) · `disabled` |

### `${VAR}` placeholders

The published manifest contains no personal data: repos, owners and hosts live only in environment variables (local: `.env` · Render: dashboard). Placeholders such as `${TICKER_REPO}` are substituted when the config is loaded; missing variables produce a warning in the log and stay literal, which makes them visible in fetch errors.

## Manager endpoints

| Endpoint | Description |
|---|---|
| `GET\|POST /tick` | **The external cron calls this every 5 minutes.** Runs every service's tick according to its schedule, plus the daily fetch on the first tick of the day. Overlap lock (409 if the previous tick is still running) |
| `GET /fetch` | Updates the scripts from GitHub immediately; if content changed → clean restart that reloads the code (10-minute anti-flapping guard) |
| `GET /services` | Service list from the manifest, with load status |
| `GET /services/{name}` | Detail of one service |
| `GET\|POST /services/{name}/{action}` | A single service's action: e.g. `GET /services/sampler/status`, `POST /services/ticker/tick` |
| `GET /status` | Aggregate state: services + last tick + per-service status |
| `GET /health` | Health check (no auth) — used by Render |
| `/{name}/...` | The service's ORIGINAL APIs, mounted 1:1 (e.g. `GET /sampler/api/data`) |

`/tick` response (illustrative — the `data` payloads come from your services):

```json
{
  "ok": true,
  "fetch": {"skipped": true},
  "services": {
    "ticker":  {"ok": true, "ms": 12,  "data": {"status": "ok", "value": 42}},
    "sampler": {"ok": true, "ms": 324, "data": {"status": "ok", "samples": 57}}
  }
}
```

## Local run

### Without Docker (recommended locally — a service that shells out to `ssh` reuses your `~/.ssh/config`)

```powershell
copy .env.example .env        # then fill in the values (set RESTART_ON_CHANGE=0 locally!)
uv sync                       # creates .venv from pyproject.toml + uv.lock
.venv\Scripts\python.exe -m uvicorn app:app --port 8765
curl http://localhost:8765/health
curl -H "X-Auth-Token: <token>" http://localhost:8765/tick
```

The bundled TUI (`manager_tui.py`) can point at the manager: set `MANAGER_URL` and `MANAGER_AUTH_TOKEN` and it authenticates with the same `X-Auth-Token`.

### With Docker (reproduces Render exactly)

```powershell
docker build -t render-manager .
docker run --rm -p 8000:10000 --env-file .env render-manager
# NB: inside the container there are NO ~/.ssh/config aliases and no
#     local keys: a service that needs ssh gets host/user/key from the
#     env vars declared in its manifest (e.g. an SSH key Secret File)
```

## Deploying to Render (step by step)

1. **Create a GitHub repository** and push this folder as is (the Dockerfile is already at the root — the build context is the root).
2. **Render → New → Web Service** → connect the repo. There is no blueprint file: configure the service manually — **Runtime: Docker** (Render builds the `Dockerfile` at the repo root; the build context is the root), **Instance Type: Free**, and **Health Check Path: `/health`**.
3. **Environment / Secret Files** (Render dashboard) — see the table below. **Secret File (recommended)**: `services.yaml` (the secret manifest, plain multiline YAML) via Environment → Secret Files — plus one more Secret File for each key a service needs (e.g. `my_ssh_key`). Then the env vars at minimum: `MANAGER_AUTH_TOKEN`, `GITHUB_TOKEN` (if any service uses `mode: api`), and every `${VAR}` placeholder your manifest references (e.g. `TICKER_REPO`, `SAMPLER_REPO`, `SAMPLER_API_KEY`). `MANIFEST_CONTENT`/`MANIFEST_REPO` are the env-var alternatives if you prefer them over the Secret File.
4. **Dedicated SSH key** (only if a service shells out to ssh): `ssh-keygen -t ed25519 -f ~/.ssh/my_ssh_key -N ""`, authorize it on the remote host, then deliver it as a Secret File (recommended, see step 3) or paste it on Render with literal `\n`: `awk '{printf "%s\\n", $0}' ~/.ssh/my_ssh_key`.
5. **cron-job.org**: ONE cron job, every 5 minutes, `GET https://<your-manager>.onrender.com/tick` with header `X-Auth-Token: <MANAGER_AUTH_TOKEN>` and a generous timeout (90-120 s, cold starts).
6. **Shut down the old services** and their crons (the manager replaces them).
7. **TUI** (optional): point it at `https://<your-manager>.onrender.com` with `MANAGER_AUTH_TOKEN` (set both in `.env`).

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `MANAGER_AUTH_TOKEN` | recommended | Protects every route except `/health` and the `public_paths` |
| `SERVICES_ENABLED` | no | Default: all services. Comma-separated manifest ids to run a subset (e.g. `ticker,sampler`); set to an empty value to run none |
| `DAILY_FETCH` | no | `1` (default) = automatic daily fetch; `0` = manual `/fetch` only |
| `RESTART_ON_CHANGE` | no | `1` (default) = restart after script updates; set `0` locally |
| Secret manifest | yes on Render | **Render Secret File** `services.yaml` (recommended; optional explicit `MANIFEST_FILE=/etc/secrets/services.yaml`) **or** `MANIFEST_CONTENT` **or** `MANIFEST_REPO` (+ `MANIFEST_BRANCH`/`MANIFEST_PATH`) |
| Service sources | yes | One env var per `${VAR}` placeholder in the manifest (e.g. `TICKER_REPO`, `SAMPLER_REPO`) |
| Service-specific vars | per service | Declared in the manifest's `env.required` / `env.optional` (e.g. `TICKER_TARGET`, `SAMPLER_API_KEY`). Prefix them with the service name to avoid collisions |

## How updates work

- **Every day**, on the first `/tick`, the manager downloads the scripts from the source repos. If content changed → clean restart → fresh code. `GET /fetch` forces it immediately.
- **Failed fetch** (repo down or unreachable) → existing copies are used and the fetch **retries at every tick** until it succeeds (self-healing). At boot, if nothing is on disk and a local `fallback/` exists (gitignored, optional), it seeds from there.
- A **new pip dependency** appearing in a script → add it to `pyproject.toml`, run `uv lock`, and redeploy: the fetch does NOT install packages. The manager logs a warning about missing dependencies at boot.

## Known limitations

- Render's filesystem is ephemeral: any local state a service keeps (files, SQLite caches) resets on every redeploy — by design, a service's source of truth should live outside the container and the service should re-initialize gracefully after a restart.
- A very unlucky tick (slow fetch + all services) can take ~3-4 minutes: cron-job.org must not overlap ticks (every 5 minutes is fine; the manager also rejects overlapping ticks with 409).
- If GitHub is unreachable at boot AND no local `fallback/` exists, services stay `script missing` until the first successful fetch (retried at every tick, then an automatic restart loads them).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `/status` shows `config_error: services.yaml not found` | no manifest on Render | set `MANIFEST_CONTENT` or `MANIFEST_REPO` (+ optional `MANIFEST_BRANCH`/`MANIFEST_PATH`) |
| Service `"loaded": false` in `/services` | missing env vars or import error | the `error` field says exactly what is missing |
| `POST /<service>/...` → 502 remote host unreachable | ssh key/host/user issues | check that service's ssh env vars and the key Secret File on Render |
| `fetch` errors 404 in `/tick` | private repo unreachable with the token | check `GITHUB_TOKEN` and the service source env vars |
| a tick returns `skipped` with a `reason` | the service decided to skip | normal: e.g. interval not elapsed, quiet hours, or disabled via `SERVICES_ENABLED` |
| Continuous restarts after a push | anti-flapping guard (10 min) | expected: at most one restart every 10 minutes |
| TUI cannot connect | wrong token or URL | check `MANAGER_URL` + the `X-Auth-Token` header (see API_GUIDELINES) |
